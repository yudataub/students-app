# אפליקציה מקומית (Desktop) — מסמך אפיון

תאריך: 2026-08-12

## הבעיה

האתר החי (`https://yudataub.github.io/students-app/`) שומר את כל הנתונים — כולל תמונות התלמידים כ-base64 — ב-`localStorage` של הדפדפן, שמוגבל לכ-5MB. עם מספיק תלמידים ותמונות (במיוחד אחרי הוספת מצב "התאמת תמונות לקיימים") האחסון מתמלא, וכל שמירה חדשה נכשלת עם השגיאה "אין מספיק מקום — נסה למחוק תלמידים ישנים".

## פתרון

אפליקציה מקומית נוספת (לא מחליפה את האתר הקיים) שרצה על מחשב המשתמש בלבד, עם שרת מקומי קטן שמחליף את `localStorage` בקובץ אמיתי על הדיסק — בלי מגבלת גודל משמעותית.

**האתר החי ממשיך להתקיים ולשמש למכשירים אחרים** (כפי שהמשתמש עובד ביותר ממכשיר אחד ומסתמך על סנכרון הענן). האפליקציה המקומית היא כלי נפרד, לשימוש במחשב הביתי/עבודה העיקרי, כשהאחסון הופך לבעיה.

## החלטות עיצוב (מאושרות עם המשתמש)

1. **חוויית הפעלה**: קובץ `הפעל.bat` — לחיצה כפולה מפעילה שרת מקומי ופותחת את האפליקציה בדפדפן ברירת המחדל של המשתמש. לא Electron / לא אפליקציה "אמיתית" עם חלון משלה.
2. **טכנולוגיית שרת**: Python (לא Node.js) — בהתאם לתשתית קיימת ומוכרת למשתמש (ר' `C:\Users\User\OneDrive\Documents\מסמכים\משחקים\YUDA\server.py` כדוגמה לדפוס דומה שכבר עובד למשתמש). שימוש רק במודולים מובנים של Python (`http.server` וכדומה) — בלי `pip install`.
3. **נגישות רשת**: `localhost` בלבד — לא נגיש מהטלפון/מכשירים אחרים ברשת הבית (בניגוד ל-YUDA). שרת יחיד, לקוח יחיד בכל זמן נתון — פשוט יותר, בלי דאגות concurrency.
4. **נתונים בהעברה ראשונית**: **עותק חד-פעמי** של הנתונים הקיימים, לא התחלה מאפס. מנגנון: כפתור ייצוא חדש באתר הקיים מוריד קובץ `backup.json` יחיד עם כל המצב (תלמידים+תמונות+ניקוד+סידורי ישיבה); מסך ייבוא חד-פעמי באפליקציה המקומית טוען את אותו קובץ בהפעלה הראשונה.
5. **סנכרון ענן**: **לא קיים** בגרסה המקומית. קוד ה-Firebase (חיבור, cloudSaveNow, cloudPullNow, כיתות משותפות) מוסר לגמרי מהעותק הזה. שתי הגרסאות (אתר + מקומי) עצמאיות זו מזו לחלוטין אחרי ההעברה החד-פעמית.

## ארכיטקטורה

```
students-app/
  index.html                 ← האתר הקיים, ללא שינוי במבנה (רק תוספת כפתור ייצוא)
  desktop/
    server.py                 ← שרת HTTP מקומי, Python סטנדרטי בלבד
    index.html                 ← עותק מותאם: שכבת אחסון מוחלפת, קוד ענן מוסר
    data/
      data.json                 ← כל מצב האפליקציה (נוצר אוטומטית בהפעלה ראשונה / בייבוא)
    הפעל.bat                  ← מפעיל את server.py ופותח דפדפן ל-http://localhost:8733
```

התיקייה `desktop/` נמצאת באותו ריפו Git (להיסטוריה/גיבוי משותפים), אך **לא מתפרסמת כחלק מהאתר החי** — GitHub Pages משרת מ-root של `main`, ו-`desktop/` הוא סתם קוד נלווה שם, לא נתיב שנגיש דרך ה-URL הציבורי. תיקיית `data/` (המכילה תמונות ילדים) חייבת להיות ב-`.gitignore` — אסור שהיא תיכנס להיסטוריית git בריפו הציבורי.

### שכבת האחסון (הליבה של השינוי)

באתר הקיים, קריאה/כתיבה סינכרונית:
```js
let students = JSON.parse(localStorage.getItem('students') || '[]');
...
localStorage.setItem('students', JSON.stringify(students));
```

בגרסה המקומית, האתחול הופך לאסינכרוני (fetch מהשרת המקומי לפני הרינדור הראשון), והכתיבות הופכות לקריאות `fetch('/api/data', {method:'POST', ...})` ברקע (fire-and-forget, כמו שהאתחול היום כבר לא חוסם על סנכרון ענן). כל שאר הקוד שמשתמש ב-`students`, `behaviorTypes`, `deletedTombstones` וכו' כמשתנים גלובליים בזיכרון — **נשאר זהה לחלוטין**, כי הם עדיין נגישים סינכרונית ברגע שהאתחול הראשוני הסתיים.

`server.py` חושף:
- `GET /api/data` — מחזיר את כל `data.json` (או אובייקט ריק אם עוד לא קיים)
- `POST /api/data` — כותב JSON גולמי חדש ל-`data.json` (כתיבה אטומית: כתיבה לקובץ זמני ואז rename, כדי למנוע קובץ חצי-כתוב אם המשתמש סוגר את השרת באמצע)
- שירות קבצים סטטיים (`index.html`) על אותו שרת

### מיפוי מפתחות localStorage → data.json

היום יש כמה מפתחות נפרדים ב-localStorage (`students`, `behaviorTypes`, `deletedTombstones`, `importedNamesMap`, `seating_<class>` מרובים). ב-`data.json` הם מאוחדים לאובייקט יחיד:
```json
{
  "students": [...],
  "behaviorTypes": [...],
  "deletedTombstones": {...},
  "importedNamesMap": {...},
  "seating": { "<className>": {...}, ... }
}
```
שכבת התאימות בקוד הלקוח (`desktop/index.html`) ממפה בין השמות הפנימיים הקיימים לבין השדות באובייקט המאוחד, כך שהלוגיקה הפנימית (למשל `saveData()`, `saveBehaviorTypes()`, `recordDeletion()`) לא צריכה לדעת על הפורמט החדש — רק שכבת ה-I/O משתנה.

### קוד שמוסר בעותק המקומי

כל מה שתלוי ב-Firebase: `initFirebase`, `_loadFirebaseSDK`, `signInWithGoogle`, `signOutUser`, `cloudSaveNow`, `cloudPullNow`, `_applyCloudData`, `_checkAndPullCloud`, `_getCloudSnapshot`, `_listenSharedClass`, `joinSharedClass`, `createSharedClass`, וכל ה-UI הנלווה (מסך הגדרות ענן, כפתורי שיתוף כיתה). כפתורי "🏆 ניקוד"/"📥 ייבא כיתה" וכו' שלא תלויים בענן — נשארים.

### ייצוא/ייבוא גיבוי (הגשר בין שתי הגרסאות)

**באתר הקיים** (`index.html`, לא ב-`desktop/`): כפתור חדש בהגדרות — "📦 ייצוא גיבוי מלא למחשב" — אוסף `students`, `behaviorTypes`, `deletedTombstones`, `importedNamesMap`, וכל מפתחות ה-`seating_*` מ-localStorage לאובייקט יחיד, ומוריד כ-`backup.json`.

**בעותק המקומי**: אם `data/data.json` לא קיים (או ריק) בעת עליית השרת, `desktop/index.html` מציג מסך ייבוא פשוט (input type=file) לפני שאר האפליקציה. בחירת `backup.json` שולחת אותו ל-endpoint חדש (`POST /api/import`) שכותב אותו כ-`data.json` הראשוני, ואז האפליקציה ממשיכה כרגיל.

## בדיקות (ידניות, כמו בכל הפרויקט — אין טסטים אוטומטיים)

1. הפעלה ראשונה: `הפעל.bat` → דפדפן נפתח → מסך ייבוא → ייבוא `backup.json` מדומה → נתונים מופיעים נכון (כולל תמונות, ניקוד, סידור ישיבה)
2. הוספת תלמיד עם תמונה גדולה, מספיק פעמים כדי לוודא שאין הודעת "אין מספיק מקום" (מבחן ישיר לבעיה המקורית)
3. שימוש בפיצ'רים קיימים ללא שינוי: ניקוד התנהגות, מבחן זיכרון, "שמות חסרים", התאמת תמונות לקיימים
4. סגירת ה-terminal (עצירת השרת) ופתיחה מחדש דרך `הפעל.bat` — הנתונים נשמרים ומופיעים כפי שהיו
5. וידוא שאין קריאות רשת ל-Firebase/אינטרנט חיצוני בגרסה המקומית (בדיקת Network tab)
6. וידוא ש-`desktop/data/` לא נכנס ל-git (`.gitignore`)

## מחוץ לתחום (לא בגרסה זו)

- גישה מהטלפון/רשת הבית
- סנכרון בין הגרסה המקומית לאתר החי אחרי ההעברה הראשונית (חד-כיווני, חד-פעמי בלבד)
- אריזה כאפליקציית Desktop אמיתית (Electron/exe מותקן)
- ריבוי משתמשים/מכשירים בו-זמנית מול אותו `data.json`
